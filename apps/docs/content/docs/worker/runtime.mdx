## Worker Health Endpoints

### GET /worker/health/live

```bash
curl http://localhost:3002/worker/health/live
```

Example response:

```json
{
  "status": "ok"
}
```

## Runtime Notes

- The worker keeps browser runtime inside the worker process, not in the API.
- Playwright browser instances are reused through a lightweight pool.
- Worker heartbeat is stored in Redis so the dashboard can list active workers.
- `WORKER_IP_TYPE` can be set to `datacenter`, `residential`, or omitted as `unknown`. This value is published in heartbeat metadata and displayed in the dashboard for routing decisions.
- `WORKER_ALLOWED_STRATEGIES` controls worker capability and can be set to `http`, `playwright`, or both as a comma-separated list. Legacy `cloudscraper` values are normalized to `http`.
- Shared non-targeted jobs are split into strategy-specific queues such as `crawlix.scrape.jobs.http` and `crawlix.scrape.jobs.playwright`.
- `strategy=auto` is published to the `http` queue by default.
- Each worker also exposes a stable `workerId` for the current runtime and consumes dedicated strategy-specific queues tied to that worker identity.
- Targeted queues now follow the same strategy-specific shape, for example `crawlix.scrape.jobs.playwright.worker.<workerId>`.
- Jobs created with `targetWorkerId` are published only to that worker-specific queue. They do not fall back to the shared queue automatically.
- The admin dashboard can list active workers and use their `workerId`, service name, hostname, strategy list, and IP type for targeted dispatch decisions.
- When a targeted job requests an incompatible strategy, the API rejects it before publish and the worker also enforces the same rule during execution.
- Terminal job events can be pushed to third-party systems through a dedicated webhook queue that is separate from the scrape execution queue.
- Webhook delivery uses its own retry and dead-letter queues, so webhook callback failures do not block scrape workers from finishing jobs.
- Workers sign outbound webhook payloads with `WEBHOOK_SIGNING_SECRET` unless the job explicitly carries its own `webhookSecret`.

## Smart Routing Examples

Use targeted dispatch when a job needs a specific worker class.

```ts
await client.createJob({
  url: "https://example.com",
  strategy: "http",
});

await client.createJob({
  url: "https://protected-target.example",
  strategy: "http",
  targetWorkerServiceName: "crawlix-worker-residential",
});

await client.createJob({
  url: "https://spa.example.com",
  strategy: "playwright",
  targetWorkerServiceName: "crawlix-worker-playwright",
});
```

- Use no target for ordinary fast HTTP jobs.
- Use `targetWorkerServiceName` for a worker pool with the same role.
- Use `targetWorkerHostname` for a known host label.
- Use `targetWorkerId` only for strict one-worker dispatch.

## Proxy Resolution

Proxy is resolved in worker runtime from each job options with this precedence:
  - if `useProxy` is `false`, no proxy is used.
  - if `useProxy` is `true` and `proxyUrl` is provided, worker uses that URL.
  - if `useProxy` is `true` and `proxyUrl` is empty, worker falls back to `SCRAPER_PROXY_URL`.
  - if both proxy values are empty, request runs direct.
